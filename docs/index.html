Geodukt

Define a DAG of ten spatial transforms in one TOML file. Geodukt works out the order, runs the graph wave by wave, and writes each sink as GeoJSON, GeoPackage, Shapefile or CSV.

Rust DAG Engine Declarative TOML GeoJSON / GeoPackage / Shapefile / CSV Built-in Transforms AGPL-3.0-or-later

Features

Declarative Pipelines

Define sources, transforms, and sinks in TOML. The file says what the pipeline is, not the order to run it in.

DAG Execution

Automatic dependency resolution. Detect cycles, validate references, then execute wave by wave, with the sources and local work inside a wave running concurrently under rayon. A source whose next steps are filter, schema_map or clip runs those on geoplumb instead, and the features come back at the first step geoplumb cannot run. Feature counts per step are the same on either path.

Spatial Transforms

Buffer, centroid, filter, clip, reproject, simplify, dissolve, expression, schema map, spatial join. The operation registry is a fixed built-in set: a manifest cannot name an operation outside it.

Multi-Format I/O

Pipeline sources and sinks read and write GeoJSON, GeoPackage, Shapefile, and CSV. CSV carries point geometry only, as lon/lat columns.

CLI Tool

geodukt run, validate, graph, init, serve, docs, diff. validate checks the graph and the required parameters without reading any data.

Trait-Based Internals

TransformOp, SourceReader and SinkWriter are public traits, so Rust code embedding the crates can assemble its own registry. Neither the CLI nor the server does: both build the default registry unconditionally, so a custom operation is not reachable from a manifest or the REST API.

Project Flags

Three switches on [project]. incremental hashes the sources and skips a run when none of them changed, lineage writes .geodukt/lineage.json after a run that finished, and quality fails a transform whose output holds invalid geometries.

Validation First

/validate and geodukt validate reject cycles, unknown inputs, duplicate names and missing required parameters before anything runs.

Execution Reports

A run record carries the feature count and status of every step, including the ones a failed run never reached.

No PROJ, GEOS or GDAL

Geometry comes from topoi and coordinate transforms from projicio. The build still needs a C toolchain for the bundled SQLite.

Pipeline Example

# geodukt.toml
[project]
name = "city-analysis"
version = "0.1.0"

[[source]]
name = "buildings"
format = "geojson"
path = "data/buildings.geojson"

[[transform]]
name = "commercial_only"
input = "buildings"
operation = "filter"
field = "type"
equals = "commercial"

[[transform]]
name = "centroids"
input = "commercial_only"
operation = "centroid"

[[sink]]
name = "output"
input = "centroids"
format = "geojson"
path = "output/commercial_centroids.geojson"

Quick Start

# Create my-pipeline/ with geodukt.toml, data/ and output/
geodukt init my-pipeline
cd my-pipeline

# Edit geodukt.toml, and put the source file it names in data/

# Validate the DAG
geodukt validate

# Run the pipeline
geodukt run

# Print the execution order
geodukt graph

# Serve the REST API
geodukt serve --bind 127.0.0.1:8080

REST API

geodukt serve exposes the pipeline over HTTP, for a UI or an agent that composes manifests and wants to check them before running.

MethodPathPurpose
GET/healthLiveness and version
GET/operationsEvery operation and format a manifest may name
POST/validateParse and check a manifest, return the plan, run nothing
POST/runExecute a manifest and record the attempt, successful or not
GET/runsThe recorded runs the caller may read, including failed ones
GET/runs/{id}One run, including the manifest it ran
GET/gp/catalogThe operations exposed as single tools: buffer, centroid, clip, dissolve, simplify
POST/gp/{tool}Run one operation over GeoJSON in the request body

/operations and /gp/catalog are generated from the tables the engine dispatches on, so the advertised parameter names are the ones the transforms read. 

# Check a manifest without running it
curl -X POST localhost:8080/validate \
  -H 'content-type: application/json' \
  -d '{"manifest": "[project]\nname = \"city\"\n..."}'

# Steps come back in execution order
{"project": "city", "version": "1.0.0", "steps": [
  {"name": "parcels", "kind": "source", "format": "gpkg", "path": "data/city.gpkg", "layer": "parcels"},
  {"name": "centers", "kind": "transform", "operation": "centroid", "input": "parcels", "params": {}},
  {"name": "out", "kind": "sink", "input": "centers", "format": "shp", "path": "out/centers.shp"}
]}

# A rejected manifest says which part to fix
{"kind": "graph", "message": "DAG error: unknown input reference: ghost"}

The kind field is toml (400, not valid TOML or not the manifest schema), graph (422, unknown input, duplicate name, or a cycle), operation (422, an operation that does not exist or a missing required parameter), or format (422, a format geodukt cannot read or write).

/run records every run that starts and answers with a run record either way, so one shape covers both outcomes. A body that is not a usable manifest is rejected before a run starts and is not recorded. A run that completes is 200 with status set to "Completed". A run that fails is 422 with status set to {"Failed": "<reason>"}, and the record stays in /runs with the manifest that produced it. 422 rather than 500 because the manifest was sound and it was the work it described that could not be carried out, so retrying it will not help.

With PLATFORM_JWT_SECRET set, /run and the /gp/* routes accept a platform JWT with the editor or admin role, or a role-free tool JWT with token_use: "tool" and scope: ["geodukt:run"]. A run records the caller's sub. Marked tool tokens never fall back to a role. An empty or wrong scope array is 403, and a missing or malformed scope claim is 401. /runs needs a token of any role: an admin reads every caller's runs, every other role reads only its own, scoped tool tokens are 403, and someone else's run is a 404. Unset means no gate, the standalone single-user flow.

The gate covers /run, /runs, /runs/{id} and every /gp/* route, /gp/catalog included. /health, /operations and /validate are open by design, so a planner or an eval harness can check a manifest without a token.

The run history is a sqlite database. GEODUKT_RUNS_DB names the file, which the server creates if it is not there and needs write access to. Unset means an in-memory database, so a restart starts an empty history.
